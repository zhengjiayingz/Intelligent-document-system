### O-01 索引断点续建（失败后续跑）· AI

**做什么**  
在「非 force 重建」时，根据已有 `document_chunks` / job 失败阶段，从失败点继续：跳过已成功的 ASR/文本提取与分块，只补 embedding / 摘要 / 知识抽取；`force: true` 仍全量清空重跑。

**为什么做**  
长音视频索引成本主要在抽轨 + ASR。当前失败后重试常 `deleteMany` chunks 再从头跑，墙钟与硅基费用重复支付；用户体感是「已经转写过又等一小时」。断点续建同时是**加速（少干活）**和**省成本**。

**怎么做**  
1. `triggerIndex`：非 force 且库中已有同 `fileHash` 的 chunks 时，**不要**无条件清空；可只清摘要/知识，或标记 `resumeFrom=embedding|summarizing`。  
2. Processor：入口探测  
   - 有 chunks 且存在 `embedding IS NULL` → 只跑 embedding 及之后；  
   - 全部已有 embedding、status 曾 failed 在 summarizing → 跳到摘要；  
   - 无可用 chunks 或 force → 全量现有流程。  
3. 日志打 `[document-index] resume from=embedding skipAsr=true` 便于验收。  
4. 前端可选：status 返回 `resumeHint`（非必须）。  

**关键路径：**  
`src/files/ai/index/processor/document-index.processor.ts`  
`src/files/ai/index/service/files-ai-index.service.ts`  
`src/files/ai/index/service/document-index-queue.service.ts`

**预期效果**  
- 人为在 embedding 失败后再点「重新建立索引」：Worker **不再**调用 ASR（日志可证）。  
- 同文件二次索引墙钟与 ASR 调用次数显著低于全量（目标：跳过提取段后接近「仅 embedding+摘要」耗时）。  
- force 全量行为与现网一致，无回归。

### O-02 向量写入批量化 · AI

**做什么**  
`embedMany` 返回后，将「逐条 `documentChunk.update` + 高频 `patchJob`」改为按批写库、按批更新进度。

**为什么做**  
N 个 chunk 约 2N 次 DB 往返，大文档在「向量已算完」后仍卡很久，属于低成本、立刻可见的延迟。

**怎么做**  
1. 批大小与 embedding 批对齐（如 32～50）。  
2. 优先：循环内减少 `patchJob`（每批或每 5～10% 一次）；进一步可用 `$executeRaw` / 临时表 / 多条 update 事务批量提交。  
3. 保持 `userFileId_chunkIndex` 正确对应，失败时该批可重试。  

**关键路径：** `document-index.processor.ts`（embedding 写库循环）

**预期效果**  
- 同 chunk 数下，embedding→DB 段耗时明显下降（常见可到数倍，视 DB RTT）。  
- 前端进度仍大致单调，不出现长时间停在 50% 却实际已算完向量。

### O-03 摘要 Map-Reduce：Map 有界并行 · AI

**做什么**  
Map 阶段对多个 chunk 的 LLM 摘要从严格串行改为有界并发（默认 4～8，env 可配）；Persist 尽量批量；Reduce 可先保持串行。

**为什么做**  
大文档 summarizing 时间 ≈ chunk 数 × 单次 LLM RTT，往往占索引后半段大头；CPU 并不忙，在等网络。

**怎么做**  
1. `summary-map-reduce.service.ts` 的 `summarizeChunks` 使用 `p-limit` 或自写信号量。  
2. env：`AI_SUMMARY_MAP_CONCURRENCY`（默认 4～8）。  
3. 控制 DeepSeek RPM/TPM，遇 429 退避降并发。  
4. 单测：mock LLM，断言并发上限与结果条数。  

**关键路径：** `src/files/ai/summary/service/summary-map-reduce.service.ts`

**预期效果**  
- 同文档、同 chunk 数，summarizing 墙钟接近「串行 / 并发度」倍速（受限流约束，实际约 3～6× 量级较常见）。  
- 摘要质量抽检不劣于串行；无大面积 429。

### O-04 `embedMany` 批间有界并行 · AI

**做什么**  
将 embedding HTTP「批与批严格串行」改为同时飞 2～3 批（env 可配）。

**为什么做**  
批内已 32 条；批间串行时总时间 ≈ 批次数 × 单批 RTT，并行可吃满带宽/服务商并发额度（在限流内）。

**怎么做**  
1. `embedding.provider.ts`：`Promise.all` + 滑动窗口，或分波次各 2～3 批。  
2. env：`AI_EMBEDDING_PARALLEL_BATCHES`（默认 2）。  
3. 单批失败只重试该批，不整文件作废（若与 O-01 配合更佳）。  

**关键路径：** `src/files/ai/index/provider/embedding.provider.ts`

**预期效果**  
- 大量 chunk 时 embedding HTTP 总等待下降（接近并行批次数的加速比，受 RPM 限制）。  
- 无系统性 400/429 回归。

### O-05 文件列表分页 + 虚拟滚动 · 网盘（非 AI）

**做什么**  
服务端 `getFiles`（及回收站列表若同类）增加分页/游标；前端列表/网格用虚拟滚动，避免一次渲染全部 DOM。

**为什么做**  
当前一次 `findMany` 无 `take`，带 storage + tags；前端全量 `v-for`。千级目录时 JSON 体积、解析与 DOM 都是明确瓶颈，与 AI 无关但影响每天打开网盘。

**怎么做**  
1. API：`limit`（默认 50～100）+ `cursor`（`id`/`createdAt`）或 page；响应带 `nextCursor` / `hasMore`。  
2. 前端：滚动加载或虚拟列表（可参考 `TextChunkPreviewDialog` 的 `@tanstack/vue-virtual`）。  
3. 可选 Prisma 复合索引 `(userId, parentId, isDeleted, createdAt)`。  
4. 兼容：旧客户端不传 limit 时可默认 limit，避免一次打爆。  

**关键路径：**  
`src/files/query/files-query.service.ts`  
`intelligent_document_frontend/src/views/index/index.vue`  
`.../views/index/cpns/FileList.vue`  
`.../views/recycle-bin/index.vue`

**预期效果**  
- 千级目录：首屏 TTFB/payload/DOM 节点显著下降。  
- 滚动流畅，不因进入大文件夹卡死主线程。

### O-06 前端包体与播放器列表 · 前端

**做什么**  
首页 Dialog/重型预览改为异步组件；管理台 echarts 按需引入并拆包；播放器文稿列表虚拟化；媒体 `preload` 改为 `metadata`。

**为什么做**  
路由虽懒加载，首页仍同步引入 Pdf/Video/Office 等，主 chunk 大、首屏慢；长 ASR 文稿全量 `v-for` 掉帧；`preload="auto"` 抢带宽。

**怎么做**  
1. `defineAsyncComponent` 包裹各 Dialog。  
2. admin：`echarts/core` + 按需图表；`vite.config.ts` `manualChunks` 拆 `echarts`/`pdfjs`。  
3. `VideoPlayerDialog` 文稿用虚拟列表；`<video preload="metadata">`。  

**关键路径：**  
`views/index/index.vue`、`components/VideoPlayerDialog/index.vue`、`vite.config.ts`、`views/admin/index.vue`

**预期效果**  
- 构建产物主 chunk 明显变小；打开「全部文件」更快。  
- 长文稿滚动帧率改善；打开播放器不至于拖垮整页下载。

### O-07 Worker 并发可配置 · 吞吐

**做什么**  
用环境变量配置 document-index（及必要时 preview）的 BullMQ `concurrency`，避免写死为 1。

**为什么做**  
多文件同时点索引时严格串行，排队线性变长；机器与 API 额度允许时提高吞吐。预览 soffice 互斥，**不能**简单与索引同样加并发。

**怎么做**  
1. `@Processor(..., { concurrency: Number(process.env.DOCUMENT_INDEX_CONCURRENCY) || 1 })`。  
2. 预览默认保持 1；文档注明 LibreOffice 风险。  
3. `.env.example` 注释推荐值（索引 1～3）。  

**关键路径：** `document-index.processor.ts`、`preview.processor.ts`

**预期效果**  
- 两文件并行索引时总完成时间短于「两倍单文件串行」（在限流允许下）。  
- 调高后无持续 embedding/LLM 429；预览默认行为不变。

### O-08 预览与索引进程隔离 · 吞吐（非 AI 为主）

**做什么**  
将 `preview-convert` 与 `document-index` 拆到不同 Node 进程（或不同机器），避免同进程抢 CPU/内存。

**为什么做**  
当前 `worker.main` 同挂两队列；LibreOffice/ffmpeg 重任务会拖慢同进程内索引 job，表现为「预览一转，索引也停」。

**怎么做**  
1. 拆脚本：`start:worker:preview` / `start:worker:index`（或 compose 两服务）。  
2. 模块可继续共用代码，仅入口注册不同 Processor。  
3. 保留预览 hash 命中快路径。  

**关键路径：** `worker.main.ts`、`preview-worker.module.ts`、部署/compose、`package.json` scripts

**预期效果**  
- 重预览进行时，轻量索引任务延迟不再同级恶化。  
- 运维可独立扩缩预览机与索引机。

### O-09 向量检索路径 · AI

**做什么**  
短期：收紧语义搜/RAG 候选规模与 SELECT 列，减少 JSON 向量拉取与内存余弦计算量。  
长期：迁入支持 ANN 的向量库（pgvector / Qdrant / Milvus 等）。

**为什么做**  
`DocumentChunk.embedding` 为 MySQL `Json`，检索实质「拉候选全量向量进 Node 算相似度」，文件与 chunk 增长后延迟与内存线性变差；schema 已注释「量大迁向量库」。

**怎么做（短期）**  
1. 限制 ready 文件数、每文件参与 chunk 上限。  
2. `select` 只取 `id, embedding, ...` 必要字段；避免多余 join。  
**怎么做（长期）**  
1. 双写或迁移 embedding 到向量库；检索改 ANN topK。  
2. 兼容层：RAG/语义搜/助手共用同一检索服务。  

**关键路径：**  
`files-search.service.ts`、`files-ai-rag.service.ts`、`files-ai-assistant.service.ts`、`prisma/schema.prisma`

**预期效果**  
- 短期：同库规模下语义搜/RAG p95 与内存峰值下降。  
- 长期：检索延迟与库规模近似解耦（ANN）。

### O-10 以图搜图指纹并行 / 预热 · AI

**做什么**  
对 gallery 候选的指纹 `ensure`（算/写 image embedding）改为有界并行，或对常用目录后台预热。

**为什么做**  
冷启动时串行 ensure 最多约 100 张，墙钟 ≈ N × 单次 VL embedding，首次搜图极慢。

**怎么做**  
1. `ImageFingerprintService` / `ImageSearchService` 中 ensure 使用并发上限（如 4）。  
2. 可选：上传图片成功后异步写指纹。  
3. 失败跳过单张，不阻断整次搜索。  

**关键路径：**  
`src/files/ai/image-search/service/image-search.service.ts`  
`src/files/ai/image-search/service/image-fingerprint.service.ts`

**预期效果**  
- 冷库首次以图搜图等待缩短（接近并发度倍速，受 API 限流）。  
- 热路径（指纹已齐）行为不变。

### O-11 分片合并上传流式化 · 上传（非 AI）

**做什么**  
合并分片时用流式读写拼接最终文件；哈希用流式 MD5，禁止整文件 `readFileSync` 进内存。

**为什么做**  
现状：每分片 `readFileSync` 再 `write`；`calculateFileHash` 整文件读入再哈希。大文件（上限可达 GB 级）会堵 Node 事件循环、内存尖峰，合并接口超时/卡死风险高。

**怎么做**  
1. `merge-upload.service.ts`：对每个 `chunkPath` `createReadStream` → `pipeline`/`pipe` 到最终 `createWriteStream`（注意背压）。  
2. `file.utils.ts`：`createHash('md5')` + 文件流 `update`，或合并过程中边写边 hash。  
3. 补单测：小文件合并哈希与现网一致；大文件用临时夹具测内存不随文件线性涨（可用监控或 mock）。  

**关键路径：**  
`src/files/upload/merge-upload.service.ts`  
`src/files/utils/file.utils.ts`

**预期效果**  
- 数百 MB～GB 合并时：接口更稳、内存峰值显著下降、事件循环无明显长时间卡死。  
- 秒传/哈希校验结果与改造前一致。

### O-12 缩略图异步生成 / 预生成 · 网盘（非 AI）

**做什么**  
避免在「缩略图 HTTP 请求」内同步跑 ffmpeg/sharp 作为主路径；改为预生成或入队异步生成，请求未命中时快速返回占位（或 202 + 占位）。

**为什么做**  
缓存命中很快；未命中时视频走 ffmpeg 抽帧，网格页 `loading=lazy` 仍会并发打多个首访，视频目录打开瞬间 CPU/IO 打满，列表体感极差。

**怎么做（推荐组合）**  
1. **预生成：** 上传完成（图片/视频）后投递轻量队列或 inline 限流生成 `{hash}-thumb.webp`。  
2. **请求路径：** 有文件则 sendFile；无则返回默认占位图，并（可选）触发一次异步生成。  
3. **限流：** 进程内同时 ffmpeg 数上限（如 1～2），防止雪崩。  

**关键路径：**  
`src/files/query/files-query.service.ts`（thumbnail ~430+）  
前端 `FileList.vue` / 缩略图 URL 工具

**预期效果**  
- 视频多的目录：打开列表不再被一串 ffmpeg 拖死；二次进入秒开（缓存）。  
- 首访可能短暂占位，可接受或显示 loading 态。

### O-13 回收站大批量还原 / 彻底删除 · 网盘（非 AI）

**做什么**  
对展开后可达大量节点的还原/彻底删除，改为批量 SQL（`updateMany`/`deleteMany`），操作日志合并或抽样，消除逐条 `findFirst` + 写日志的 N+1。

**为什么做**  
软删已批量；还原/硬删在展开上限（可达 1 万）内逐条处理时，连接占用与延迟随节点数线性恶化，大文件夹「清空回收站」会卡住。

**怎么做**  
1. 按 `userId` + id 列表（或父树展开结果）分批 `updateMany` / `deleteMany`（每批数百～数千）。  
2. 操作日志：一条汇总（含 count + 样例 id）或每批一条，避免一万条 insert。  
3. 保持权限与「仅自己的文件」校验。  

**关键路径：** `src/files/manage/files-manage.service.ts`

**预期效果**  
- 大文件夹批量还原/清空：耗时与 DB 往返次数下降一个数量级量级（视批大小）。  
- 小批量行为与权限语义不变。  
- **优先级说明：** 无真实「整树清空」痛点时可后置。
